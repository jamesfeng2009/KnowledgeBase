# 向量索引优化指南

> 本指南聚焦 pgvector 向量索引的选型、参数调优、性能对比与最佳实践，帮助在召回率与延迟间取得平衡。

## 1. 索引类型选型

pgvector 支持三种近似最近邻（ANN）索引：

| 索引 | 算法 | 特点 | 适用场景 |
| --- | --- | --- | --- |
| IVFFlat | 倒排文件 | 构建快，内存占用小 | 中小规模、快速上手 |
| HNSW | 层级小世界图 | 查询快、召回高，内存占用大 | 中大规模、低延迟 |
| IVF + PQ | 乘积量化压缩 | 内存占用极小，召回略降 | 超大规模、内存受限 |

EnterpriseKB 默认推荐 HNSW。

## 2. HNSW 索引详解

### 2.1 构建参数

```sql
CREATE INDEX idx_chunks_embedding
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

| 参数 | 含义 | 默认 | 影响 |
| --- | --- | --- | --- |
| m | 每层最大连接数 | 16 | 越大召回越高、内存越大 |
| ef_construction | 构建时搜索宽度 | 64 | 越大索引质量越高、构建越慢 |

### 2.2 查询参数

```sql
SET hnsw.ef_search = 80;
SELECT id FROM document_chunks
ORDER BY embedding <=> $1 LIMIT 5;
```

`ef_search` 控制查询时的搜索宽度，越大召回越高、延迟越高，可在会话级动态调整。

## 3. 参数调优方法

### 3.1 调优流程

1. 建立评测集（查询 + 相关文档标注）
2. 固定其他参数，单变量调整
3. 记录 Recall@k 与 P95 延迟
4. 选择满足 Recall 目标的最低延迟配置

### 3.2 推荐配置矩阵

| 数据规模 | m | ef_construction | ef_search | 预期 Recall@10 |
| --- | --- | --- | --- | --- |
| 10万 | 12 | 48 | 40 | 0.93 |
| 100万 | 16 | 64 | 80 | 0.96 |
| 1000万 | 24 | 128 | 120 | 0.97 |

### 3.3 调参示例脚本

```python
import psycopg2

configs = [(16, 64, 80), (24, 128, 120)]
for m, efc, efs in configs:
    conn = psycopg2.connect(...)
    conn.execute(f"SET hnsw.ef_search = {efs}")
    # 跑评测集，统计 recall 与 latency
    recall, p95 = run_eval(conn, golden_set)
    print(f"m={m}, efc={efc}, efs={efs}: recall={recall}, p95={p95}ms")
```

## 4. 距离度量选择

| 度量 | 操作符 | 适用模型 |
| --- | --- | --- |
| 余弦相似度 | `<=>` | OpenAI 等归一化向量 |
| 内积 | `<#>` | 已归一化且需加速 |
| L2 距离 | `<->` | 部分本地模型 |

> 索引必须与查询使用相同的距离操作符，否则索引失效退化为全表扫描。

## 5. 性能对比

### 5.1 HNSW vs IVFFlat（百万级）

| 指标 | HNSW | IVFFlat |
| --- | --- | --- |
| 索引构建耗时 | 16min | 6min |
| 索引大小 | 1.2GB | 680MB |
| 查询 P95 | 105ms | 180ms |
| Recall@10 | 0.96 | 0.91 |

### 5.2 不同 ef_search 延迟召回曲线

| ef_search | P95 延迟 | Recall@10 |
| --- | --- | --- |
| 40 | 70ms | 0.91 |
| 80 | 105ms | 0.96 |
| 160 | 180ms | 0.98 |
| 320 | 340ms | 0.99 |

边际收益递减，80 通常是性价比最优点。

## 6. 索引维护

### 6.1 重建与碎片

频繁增删会导致 HNSW 图碎片化，召回下降。定期重建：

```sql
-- 在线重建（不阻塞写入，pg16+）
REINDEX INDEX CONCURRENTLY idx_chunks_embedding;
```

### 6.2 统计信息更新

大量数据变更后更新统计信息，帮助查询计划器：

```sql
ANALYZE document_chunks;
```

### 6.3 监控指标

- 索引大小增长
- 查询命中率与降级为全表扫描次数
- 平均查询延迟与 P99 抖动

## 7. 内存与配置

HNSW 索引尽量常驻内存，建议：

- `shared_buffers` 设为内存的 25%
- `effective_cache_size` 设为内存的 75%
- 索引大小超过内存时性能急剧下降，考虑分片

## 8. 分片策略

千万级以上向量建议分片：

- **按租户分片**：天然隔离，路由简单
- **按时间分片**：旧数据查询少，可降低 ef_search
- **哈希分片**：均匀分布，需跨片合并

查询时并行检索各分片，结果合并后重排序。

## 9. 常见陷阱

1. **忘记建索引**：查询全表扫描，千万级数据卡死
2. **度量不匹配**：索引用 cosine，查询用 L2，索引失效
3. **维度不一致**：模型变更未重建索引
4. **ef_search 过低**：召回率不达标
5. **内存不足**：索引落盘导致延迟飙升

## 10. 最佳实践总结

- 中大规模优先 HNSW，`m=16, ef_construction=64`
- 查询 `ef_search` 从 80 起步，按评测微调
- 距离度量与索引、模型保持一致
- 定期重建索引与更新统计信息
- 千万级以上引入分片

> 索引调优没有银弹，必须基于真实数据与评测集量化决策。
