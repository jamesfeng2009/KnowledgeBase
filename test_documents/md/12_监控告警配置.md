# 监控告警配置

> 本文档说明 EnterpriseKB 的监控指标体系、告警规则、Dashboard 配置与 On-call 流程。

## 1. 监控架构

```
[应用] --暴露/metrics--> [Prometheus] --存储--> [Grafana 可视化]
                                  |
                          [Alertmanager] --通知--> [飞书/钉钉/邮件]
```

- 指标采集：Prometheus 拉取模式，15s 间隔
- 日志采集：Filebeat -> Elasticsearch
- 链路追踪：OpenTelemetry -> Jaeger

## 2. 核心监控指标

### 2.1 业务指标

| 指标 | 类型 | 说明 |
| --- | --- | --- |
| ekb_retrieve_total | Counter | 检索请求总数 |
| ekb_retrieve_duration_seconds | Histogram | 检索耗时分布 |
| ekb_ask_total | Counter | 问答请求总数 |
| ekb_ask_errors_total | Counter | 问答失败数 |
| ekb_llm_tokens_total | Counter | LLM token 消耗 |
| ekb_index_pending | Gauge | 待索引文档数 |

### 2.2 系统指标

| 指标 | 说明 |
| --- | --- |
| process_cpu_seconds_total | CPU 使用 |
| process_resident_memory_bytes | 内存使用 |
| postgres_connections | 数据库连接数 |
| redis_connected_clients | Redis 连接数 |
| http_request_duration_seconds | HTTP 请求耗时 |

## 3. 告警规则

### 3.1 关键告警（P0，立即响应）

```yaml
groups:
  - name: ekb-critical
    rules:
      - alert: EkbApiDown
        expr: up{job="ekb-api"} == 0
        for: 2m
        labels: {severity: critical}
        annotations:
          summary: "EKB API 不可用"

      - alert: EkbHighErrorRate
        expr: |
          rate(ekb_ask_errors_total[5m]) / rate(ekb_ask_total[5m]) > 0.1
        for: 5m
        labels: {severity: critical}
        annotations:
          summary: "问答错误率超过 10%"
```

### 3.2 警告告警（P1，工作时间内响应）

| 告警 | 触发条件 | 持续 |
| --- | --- | --- |
| 检索延迟高 | P95 > 1.5s | 10m |
| 索引堆积 | pending > 500 | 15m |
| 数据库连接高 | 连接数 > 80% 上限 | 5m |
| 磁盘使用高 | 使用率 > 85% | 5m |
| LLM 超时增多 | 超时率 > 5% | 10m |

### 3.3 通知策略

- P0：电话 + 飞书 + 邮件，全天 24 小时
- P1：飞书 + 邮件，工作时间段
- P2：仅记录，日报汇总

## 4. Grafana Dashboard 配置

### 4.1 主看板布局

1. **概览行**：QPS、错误率、P95 延迟（单值面板）
2. **检索行**：检索量时序图、耗时分位数图
3. **LLM 行**：Token 消耗、模型调用耗时、降级次数
4. **资源行**：CPU/内存/连接数时序图
5. **队列行**：待索引文档数、Worker 处理速率

### 4.2 变量配置

```json
{
  "datasource": "Prometheus",
  "templating": {
    "list": [
      {"name": "tenant", "query": "label_values(ekb_retrieve_total, tenant_id)"},
      {"name": "instance", "query": "label_values(up{job=\"ekb-api\"}, instance)"}
    ]
  }
}
```

## 5. 日志监控

### 5.1 关键日志关键词

- `ERROR` / `CRITICAL`：异常堆栈
- `traceback`：Python 异常
- `timeout`：超时事件
- `OOM`：内存溢出

### 5.2 日志告警

通过 Elasticsearch Watcher 或 Loki Ruler 配置：错误日志 5 分钟内超过 50 条即告警。

## 6. 链路追踪

启用 OpenTelemetry 后，每个请求携带 `trace_id`，可在 Jaeger 中查看：

- API -> 检索引擎 -> 数据库 各段耗时
- Worker 任务执行链路
- LLM 调用耗时与重试

## 7. On-call 流程

### 7.1 响应时效

| 级别 | 响应时间 | 解决时间 |
| --- | --- | --- |
| P0 | 5 分钟 | 1 小时 |
| P1 | 30 分钟 | 4 小时 |
| P2 | 工作日处理 | 1-2 天 |

### 7.2 处理步骤

1. 收到告警通知，确认是否误报
2. 在 On-call 群响应「收到」
3. 登录 Dashboard 定位问题
4. 采取临时止血措施（限流、降级、重启）
5. 根因分析并彻底修复
6. 编写故障复盘文档

### 7.3 升级机制

- P0 未在 5 分钟响应，自动升级到备岗
- 超过 30 分钟未解决，升级到 Tech Lead

## 8. 告警治理

- 每月 review 告警有效性，清理长期不触发的规则
- 降噪：相关告警聚合，避免告警风暴
- 每条告警须有可执行的处理 Runbook

> 好的监控是「信噪比高」的监控，宁缺毋滥。
