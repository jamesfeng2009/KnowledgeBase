关键问题

  1. 熔断器覆盖不完整：仅 3 个 LLM Provider 有熔断器保护，Embedder/Reranker/VectorStore 完全裸奔。当 OpenSearch 或 TEI 服务宕机时，每个请求都会等待超时后才失败，无快速失败机制。
  2. 健康检查无调度：VectorStoreBase.health_check() 抽象方法已定义且两个实现都有具体实现，但从未被定时调用。系统无法主动感知服务状态变化。
  3. 熔断器 OPEN 即中断：当前 VLLMProvider/DashScopeProvider/AnthropicProvider 在熔断器 OPEN 状态直接抛出 CircuitBreakerOpenError，无故障转移到备用 Provider 的机制。
  4. 单 Provider 模式：get_llm_provider() / get_embedder() / get_reranker() 均返回单一实例，无备用 Provider 池。

架构设计

设计目标

  1. 所有 AI 服务 Provider 统一熔断器保护（LLM + Embedder + Reranker + VectorStore）
  2. 定时健康检查调度（Celery Beat 每 30s 执行），结果存 Redis
  3. Provider 故障转移链 — 主 Provider 熔断时自动切换到备用 Provider
  4. 统一健康状态 API + 前端监控面板

整体架构

用户请求
  │
  ▼
ProviderPool（故障转移层）
  │ ├── 主 Provider（熔断器 CLOSED → 正常调用）
  │ ├── 备用 Provider 1（主熔断 OPEN → 自动切换）
  │ └── 备用 Provider 2（备用 1 也熔断 → 再切换）
  │
  ▼
实际 Provider 调用（embed / rerank / search / chat）
  │
  ▼
熔断器记录成功/失败
  
HealthCheckScheduler（Celery Beat 30s）
  │ ├── 调用所有 Provider 的 health_check()
  │ ├── 结果写入 Redis（health:provider:{name}, TTL=60s）
  │ └── 更新熔断器状态（连续失败 → 强制 OPEN）

组件 3: ProviderPool 故障转移

# app/llm/provider_pool.py

class ProviderPool(Generic[T]):
    """Provider 池 — 管理主/备 Provider，自动故障转移。
    
    当主 Provider 的熔断器处于 OPEN 状态时，自动切换到下一个备用 Provider。
    所有 Provider 的熔断器都处于 OPEN 时，抛出 AllProvidersUnavailableError。
    """
    
    def __init__(self, providers: list[T], get_breaker_name: Callable[[T], str]):
        self._providers = providers
        self._get_breaker_name = get_breaker_name
        self._current_index = 0
    
    async def call(self, method: str, *args, **kwargs):
        """调用当前 Provider 的方法，熔断时自动切换。"""
        for i, provider in enumerate(self._providers):
            breaker = get_circuit_breaker(self._get_breaker_name(provider))
            if breaker.state == CircuitState.OPEN:
                if not breaker._should_transition_to_half_open():
                    continue  # 跳过熔断中的 Provider
            try:
                # 尝试调用
                result = await getattr(provider, method)(*args, **kwargs)
                self._current_index = i
                return result
            except CircuitBreakerOpenError:
                continue
            except Exception:
                breaker._record_failure()
                continue
        raise AllProvidersUnavailableError(...)

P2-B: 查询重写/扩展

现状分析

当前检索流程

用户原始查询 (raw query)
  │
  ▼
AgenticRAGEngine._retrieve()
  │  query = state["query"]                    ← 原始查询，无任何改写
  │
  ▼
HybridRetriever.search(query, kb_ids, top_k)
  │  ├── _vector_search: embed([query])        ← 原始查询向量化
  │  └── _fulltext_search: multi_match(query)  ← 原始查询全文检索
  │
  ▼
Reranker.rerank(query, documents, top_k)       ← 原始查询重排
  │
  ▼
QualityGuard.check_retrieval_quality()          ← 后置检查：分数低则扩展 top_k
  │
  ▼
Generator.generate(query, retrieved_docs)       ← 生成回答

关键问题

  1. 无查询扩展：用户输入"报销"时，系统不会扩展为"报销 + 费用报销 + 报销流程 + 报销单据"，导致向量检索和全文检索召回不足。
  2. 无查询分解：复杂问题如"Qwen 和 Llama 在长文本处理上的区别是什么？"被当作单一查询处理，无法分别检索 Qwen 和 Llama 的相关文档再合并。
  3. 无 HyDE：向量检索使用原始查询的嵌入，而非"假设答案"的嵌入。研究表明 HyDE 可提升向量检索召回率 10-20%。
  4. 无查询分类：所有查询走同一条路径。简单事实型查询不需要 LLM 改写，对话型查询需要上下文补全，分析型查询需要分解。
  5. QualityGuard 是后置补救：只在检索结果质量差时扩展 top_k 重排，不在检索前优化查询本身。

架构设计

设计目标

  1. 可插拔查询重写管线 — 策略可独立开关
  2. 零 LLM 调用策略（同义词扩展）优先，LLM 策略（HyDE/分解）可选 + 缓存
  3. 查询分类路由 — 按查询类型选择重写策略
  4. 成本控制 — 重复查询缓存命中时零 LLM 调用

查询重写管线

用户原始查询
  │
  ▼
QueryClassifier（查询分类）
  │  ├── Factual（事实型）    → QueryExpansion only
  │  ├── Analytical（分析型） → QueryExpansion + Decomposition
  │  └── Conversational（对话型）→ ContextCompletion（上下文补全）
  │
  ▼
QueryExpansion（查询扩展 — 零 LLM 调用）
  │  ├── 领域同义词词典（企业知识库术语映射）
  │  ├── 通用同义词扩展
  │  └── 输出：扩展后的查询字符串
  │
  ▼（可选）

  │  ├── 检测多部分问题
  │  ├── 分解为子查询列表
  │  └── 每个子查询独立检索后合并
  │
  ▼（可选）

  │  ├── LLM 生成假设性答案
  │  └── 用假设答案嵌入替代原始查询嵌入（仅影响向量检索）
  │
  ▼

策略详细设计

策略 1: QueryExpansion（零 LLM 调用）

# app/rag/query_rewriter.py

class QueryExpansion:
    """查询扩展 — 同义词 + 相关词注入，零 LLM 调用。"""
    
    # 领域词典 — 可通过配置文件覆盖
    DOMAIN_SYNONYMS: dict[str, list[str]] = {
        "报销": ["费用报销", "报销流程", "报销单据", "费用申请"],
        "请假": ["休假", "调休", "年假", "事假", "病假"],
        "入职": ["onboarding", "新员工", "入职流程"],
        # ... 更多领域术语
    }
    
    async def expand(self, query: str) -> str:
        """扩展查询 — 匹配领域词典，注入同义词。"""
        words = self._tokenize(query)
        expanded_terms = set()
        for word in words:
            if word in self.DOMAIN_SYNONYMS:
                expanded_terms.update(self.DOMAIN_SYNONYMS[word])
        if expanded_terms:
            return f"{query} {' '.join(expanded_terms)}"
        return query

策略 2: QueryDecomposition（1 LLM call, cached）

class QueryDecomposition:
    """查询分解 — 将复杂多部分问题分解为子查询。"""
    
    DECOMPOSE_PROMPT = """分析以下用户查询，判断是否需要分解为多个子查询。
    
用户查询: {query}
    
规则:
- 如果查询包含多个独立子问题（如"A和B的区别"、"A的X以及B的Y"），分解为子查询。
- 如果查询是单一问题，返回原查询。
    
输出JSON格式:
{{"need_decompose": true/false, "sub_queries": ["子查询1", "子查询2"]}}
"""
    
    async def decompose(self, query: str) -> list[str]:
        # 1. 检查 Redis 缓存
        cache_key = f"query_decompose:{sha256(query)}"
        cached = await redis.get(cache_key)
        if cached:
            return json.loads(cached)
        
        # 2. LLM 调用
        result = await llm.chat([{"role": "user", "content": self.DECOMPOSE_PROMPT.format(query=query)}])
        parsed = json.loads(result)
        
        # 3. 缓存 (TTL=1h)
        sub_queries = parsed.get("sub_queries", [query])
        await redis.setex(cache_key, 3600, json.dumps(sub_queries))
        
        return sub_queries

策略 3: HyDE（1 LLM call, cached）

class HyDE:
    """Hypothetical Document Embeddings — 生成假设答案用于向量检索。"""
    
    HYDE_PROMPT = """请基于以下问题，写一段简短的假设性答案（50-100字）。
不需要准确，只需包含可能相关的关键词和概念。
    
问题: {query}
    
假设性答案:"""
    
    async def generate(self, query: str, embedder) -> list[float]:
        # 1. 检查 Redis 缓存
        cache_key = f"query_hyde:{sha256(query)}"
        cached_embedding = await redis.get(cache_key)
        if cached_embedding:
            return json.loads(cached_embedding)
        
        # 2. LLM 生成假设答案
        hypothetical_doc = await llm.chat([{"role": "user", "content": self.HYDE_PROMPT.format(query=query)}])
        
        # 3. 嵌入假设答案
        embedding = (await embedder.embed([hypothetical_doc]))[0]
        
        # 4. 缓存 (TTL=1h)
        await redis.setex(cache_key, 3600, json.dumps(embedding))
        
        return embedding

查询分类

class QueryClassifier:
    """查询分类 — 按类型路由到不同重写策略。"""
    
    async def classify(self, query: str, context: str = "") -> QueryType:
        """规则优先，LLM 兜底。"""
        # 规则 1: 包含代词且无上下文 → 对话型
        if any(pronoun in query for pronoun in ["它", "他", "她", "这个", "那个", "上面"]):
            if not context:
                return QueryType.CONVERSATIONAL
        
        # 规则 2: 包含对比/多部分关键词 → 分析型
        analytical_markers = ["和", "与", "对比", "区别", "以及", "同时", "分别"]
        if sum(1 for m in analytical_markers if m in query) >= 2:
            return QueryType.ANALYTICAL
        
        # 规则 3: 默认事实型
        return QueryType.FACTUAL

成本控制

策略LLM 调用缓存延迟
QueryExpansion0不需要~1ms（字典查找）
QueryDecomposition≤1（缓存命中时 0）Redis, TTL=1h~200ms（未命中）/ ~1ms（命中）
HyDE≤1（缓存命中时 0）Redis, TTL=1h~500ms（未命中）/ ~1ms（命中）
QueryClassifier0（规则优先）不需要~1ms

最坏情况：每次查询 2 LLM 调用（Decomposition + HyDE）
最佳情况：0 LLM 调用（Factual 查询 + 缓存命中）
默认配置：HyDE 关闭，Decomposition 开启，Expansion 始终开启
