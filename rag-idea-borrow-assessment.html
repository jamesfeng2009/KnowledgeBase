借鉴评估：Research Agent 文章 → 本项目落地

目标：只取理念、不动技术栈（不引入 LangGraph / Chroma / FastMCP 标准协议），并评估公网混合检索纳入 P 规划的合理性。 · 2026-08-20
总体结论

文章的技术栈（LangGraph StateGraph、Chroma、FastMCP）与本项目刻意移除 LangGraph / 禁止 SQLite / MCP 仅内部工具注册表 / RAG 核心手写四条约束直接冲突，全部不采纳。但其 5 条框架无关的设计理念中：2 条本项目已实现且更彻底（引用溯源）、2 条值得低成本照搬理念（生成阶段内部优先、归一化合并）、1 条正是真实空白（公网混合检索，且与已存在的 DeepResearch 场景高度契合）。

Part A · 只取理念，落地对照清单

对照"文章做法 → 本项目现状 → 框架无关的落地动作 → 归属"。总原则：任何落地都不得重新引入 LangGraph / Chroma / 快照式 interrupt，恢复/暂停一律用现有 Celery 里程碑 Checkpoint 或 UI 两段式完成。

1「先对齐需求再动手」的 HITL 澄清 + 大纲审核 理念可借鉴

文章：用 interrupt() 把图在「需求澄清 / 大纲审核」两处停住，等人类通过 Command(resume) 回填后继续；LLM 副作用与 interrupt 拆成两个节点，避免 resume 重跑产生对不上的问题。

本项目现状：已有 planner + engine 的规则级 Clarify / Interrupt 出口（零 LLM 成本）；DeepResearchService 已有 _decompose_goal（LLM 拆子课题）+ Celery milestone_checkpoint 断点恢复（P2-11 / P2-13）。缺的是"用户主动确认报告骨架"这一步。

落地（不动栈）：不引入快照式 interrupt。改由业务层实现两段式——① _decompose_goal 产出子课题骨架后先落成"待确认"中间态并返回给前端；② 用户在前端增删改章节后再次提交，才用确认后的骨架进入检索阶段。暂停/恢复完全依赖现成的 Celery + 里程碑 Checkpoint，"等人类"只是任务处于 awaiting_review 状态、无需占用 LLM。LLM 副作用放 _decompose_goal、确认态只做回填，天然规避"重跑对不上"。

2双源归一化合并（内部向量分数 vs 网络分数量纲不同）真实空白

文章最实的一条：余弦相似度（0~1）与 Tavily 搜索相关性分（另一套量纲）不能直接比大小，必须「先各自 min-max 归一化 → 内部 × BOOST → 再合并排序」；且不能用手写"固定配额拼接"，否则 boost 参数形同虚设。改为保底配额 + 剩余预算全局竞争。

本项目现状：HybridRetriever.gather_paths 四路（vector / fulltext / cross_modal / graph）均为内部源、量纲接近，因此目前不存在跨源合并问题——这是"当下无需处理、一旦接公网必须先做"的关键点。

merge_rank(internal, web)：归一化 internal & 归一化 web → 内部 × boost → 合并排序 → 保底 internal[:min] + web[:min] → 剩余预算两源候选池 加权全局竞争 → 按分收尾

落地：仅在启动公网检索 Part B 时实现 merge_rank.py（纯函数，无框架依赖，可独立单测）。现阶段的"保底+竞争"算法验收项：改 boost 需能在报告引用占比上观察到变化（否则该参数是死的）。

3「内部优先」放在生成阶段，而非检索阶段 理念可借鉴 · 低风险即收益

文章：不在检索排序里强行给内部加权（会破坏双源公平合并），而是在 Summarize 的 Prompt 里约束「内部已清晰回答就优先引用，网络仅作补充」，调参直观、效果可观察。

本项目现状：DeepResearchService._summarize 已接收带来源标注的 EvidenceCard，但未显式施加"内部优先"的 Prompt 约束。

落地：在 _summarize 的系统提示里加一段"内部证据优先 / 网络仅补充最新信息 / 每个论点后标 [n]"。独立可交付、半天工作量、不动任何架构，可先行在 DeepResearch 体验上验证。

4引用可溯源 + 悬空编号清理 项目已领先 · 无需借鉴

文章：报告每条引用标 [内部文档]/[网络]，编号经代码层校验，LLM 幻觉出的编号被自动清理（strip_dangling_citations）。

本项目现状：项目记忆与代码均显示——引擎强制调用 extract_citations() 生成结构化引用卡片；EvidenceCard；evidence_ref 四层贯穿（engine → TraceContext → SpanRecord → ToolAuditLog）；P1/P2/P3 正是为此把"依据 / 证据"落库做深。这些远超文章。

结论：此条不落地，仅需在引用展示时给来源打上「内部/网络」标签（属前端展示件）。

5双生命周期集合：持久知识库 vs 任务临时记忆 理念可借鉴 · 间接

文章：enterprise_kb 跨任务永久共享 vs research_{job_id} 单任务临时分片（用完即弃 / TTL），避免污染全局知识库、保证任务隔离。

本项目现状：多租户隔离（RLS / 密级 / 租户级过滤）已覆盖全局知识库；但 DeepResearch 若需"抓取公网页面的临时正文分片"，目前无任务级临时工作记忆。

落地：仅当启用公网检索（Part B）时，为"抓取到的外网页正文"建立任务隔离的临时索引 + TTL 清理，或在内存中对每个子课题暂存抓取结果。不必照搬 Chroma 的 collection 语义——用 Milvus 的任务级 collection 或直接在流程内存里暂存即可。

明确不落地的技术栈（全部否决）
LangGraph StateGraph Chroma（SQLite） FastMCP 标准协议落地 interrupt() 快照式暂停

理由：分别违背"LangGraph StateGraph 保持移除 / 禁用 SQLite / MCP 内部工具注册表不实现标准协议 / RAG 核心手写"四条既定约束；这些能力本项目已用「单路径 while 循环 + 多记忆层 + Milvus/OpenSearch」等价或更完整地实现。理念可取，工具不取。

Part B · 公网混合检索 纳入 P 规划的评估

判断它该不该做、放哪个阶段、工作量与风险。结论先行：建议作为独立新增工作流（暂定 P4-前沿）立项，不并入现 P1/P2/P3；先 POC 验证双源合并算法，再做正式集成。

① 与 P1/P2/P3 的关系：正交，不冲突

现有阶段实质内容与公网检索关系
P1仲裁理由 verdict_reason + 遗忘原因/激活值落库记忆层"为什么"可审计，无关
P2state.update 摘要 + 工具审计补全（result_ref/evidence_ref）轨迹差分与审计，无关
P3evidence_ref 贯穿四层（纯 plumbing）证据通道，不冲突，公网证据未来可复用此通道外引
建议：公网混合检索属检索层 + DeepResearch 能力，与 P1/P2/P3 的"记忆审计链路"正交。塞进既有 P1/P2/P3 会挤占既定交付节奏、破坏"一次一个关注点"；应独立成新工作流，依赖 P3 的证据通道（可后置联调）。

② 场景契合度：高，且恰有载体

是否有"课题/研究报告"类产品能力DeepResearchService（P2-11 调研 + P2-13 里程碑断点）已存在★ 有现成载体

判据本质：产品是否要求"研究报告 / 竞品分析"类能力？若收敛为"是"，公网检索就是对 DeepResearch 最高性价比的补强。

③ 现状缺口清单（落地则需补齐）

  1. 新增一条检索 gather 路径：HybridRetriever.gather_paths 增加 source="web" 分支（纯新增，不动既有四路）。
  2. 扩展 _gather_evidence：从"只查内部 retriever.search"改为"内部 + 公网并发（asyncio.gather，单路失败降级不阻塞）"。并发 ≤ 2 的约束需注意（对齐爬虫/外部调用防 IP 屏蔽的既有偏好）。
  3. 接入一个公网搜索提供商：Tavily / Bing / 通义等搜索 API，需选型 + 成本控制（对齐你"追踪并限制外部服务用量、避免意外成本"的强偏好，按租户配额）。
  4. 实现 merge_rank.py：归一化 + 内部 boost + 保底/竞争（见 Part A #2），另需**来源编号去重 + 引用标签**。
  5. 任务级临时工作记忆 + 内容安全：抓取正文分片做任务隔离 + TTL；公网内容 sanitize 防注入 / 防污染，来源白名单 + 质量门槛（对齐注入防护安全约束）。

决策要点（给评审的一句话）
公网混合检索是对已存在的 DeepResearch 最直接的补强，属独立检索能力而非记忆审计，应与 P1/P2/P3 并列推进、互不阻塞；建议先立 POC（半周）验证 merge_rank 的归一化+保底+竞争算法可观察，通过后再作为正式立项，再接提供商与前端引用标签。全程不引入 LangGraph / Chroma。
